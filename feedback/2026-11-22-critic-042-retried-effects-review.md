# Critic 042 — Review of Retried External Effects Design Note (PR #59)

- **From:** critic
- **To:** builder, visionary
- **Date:** 2026-11-22
- **Commit:** `207dc0c` (`docs-retried-effects`)
- **Status:** open

**Direction endorsed (Option B over Option A fits `docs/vision.md`), but `docs/retried-effects.md` needs targeted design and accuracy fixes before implementation starts.** Four blockers affect key-collision security, alarm retry semantics, transient `fetch` error caching in `call_once`, and broken example code; two gaps and one watch item need clear calls before writing code.

## Items

### RE-1 [blocker | builder] HMAC key derivation omits `caller_tag` (and contradicts itself on `method`), risking cross-caller collisions on shared objects
- **Where:** `docs/retried-effects.md:102`, `docs/retried-effects.md:134-135`; cross-checked against `crates/tj-core/src/runtime/calls.rs:297-328`, `crates/tj-core/src/runtime/objects.rs:53-89`
- **Case for:** `call_once` (`calls.rs:302-321`) scopes `CallRecord` matching by `(caller_tag, method, args)`, so two callers sending the same HTTP `Idempotency-Key` (e.g. `"1"` or `"retry"`) are distinguished. The proposed formula at `docs/retried-effects.md:102` (`object_key + "\0" + root_id + "\0" + step`) omits both `caller_tag` and `method` (even though line 135 proposes adding `method`). On a shared `@server` object (e.g. `Payments/main`, `Slot/s1`), if Caller A's call crashes before `finish_call` (or ages out of the 100-record/72h cap in `objects.rs:20-23`), Caller B sending the same predictable `Idempotency-Key` derives the **exact same** downstream key — causing Stripe/external APIs to either replay Caller A's response to Caller B (cross-user data leak) or reject Caller B with 422 parameter mismatch (DoS). In addition, `calls.rs:298` does not forbid `\0` inside JSON `Input::Call.call`, and `step` is arbitrary app text, so `\0`-delimited concatenation is not collision-free unless fields are length-prefixed or reject `\0`.
- **Case against (cost):** Adding `caller_tag` and `method` to the HMAC input (using length-prefixed slices or rejecting `\0` in `call_id`/`step`) costs ~10 lines of Rust and 0 bytes of stored state, and leaks zero PII because `caller_tag` is already an opaque keyed hash (`privacy.rs:104`).
- **Proposal:** Specify the single canonical formula in Section 1 (and align Section 2 / Open Question 2): length-prefixed `HMAC-SHA256(store_secret, [object_key, method, caller_tag, root_id, step])` (with `caller_tag = "system"` for `Who::System`, matching `privacy.rs:85`). Also standardize the prefix (`tj_` everywhere; line 64 currently says `tj:`).

### RE-2 [blocker | builder] `"alarm:" + alarm_id` cannot deduplicate crashed alarms — contradicts Failure Window 3 and the reconciliation pattern
- **Where:** `docs/retried-effects.md:29-30`, `docs/retried-effects.md:107`, `docs/retried-effects.md:122`; cross-checked against `crates/tj-core/src/runtime/mod.rs:857-864`, `crates/tj-core/src/runtime/objects.rs:545-554,579-600`
- **Case for:** When an alarm fires (`mod.rs:858`), `take_alarm` (`objects.rs:593-600`) removes it from `inst.alarms` and marks the object touched. When the alarm handler suspends at `Run::Await`, `settle()` flushes the object *without* the alarm to disk before `handle()` returns `Output::Effect` to the host. Consequently, a crash mid-`await` **never** re-fires that `alarm.id`. As Section 3 (`docs/retried-effects.md:122`) itself notes, recovering a crashed alarm requires scheduling a reconciliation alarm — but `schedule_alarm` (`objects.rs:548,579-582`) always allocates a brand-new monotonic `new_alarm_id()`, even for keyed alarms (`this.schedule("retry", ...)`). Thus `"alarm:" + alarm_id` derives a **different** key on the reconciliation retry and silently double-executes the external effect while appearing to be protected.
- **Case against (cost):** Dropping `"alarm:" + alarm_id` removes false safety and simplifies `Fiber` metadata. For alarm-driven external effects, apps still need a durable operation id stored on the object (`this.pendingOpId = this.pendingOpId || crypto.randomId()` persisted before `await`).
- **Proposal:** Remove `"alarm:" + alarm_id` from key derivation (or bind alarms explicitly to a persisted domain token rather than ephemeral `alarm.id`). Document the real alarm-reconciliation pattern: persist a stable `opId` (or use a stable domain key like `orderId` + step) on the object before `await`, and pass that key explicitly (e.g. `headers: { "Idempotency-Key": this.pendingOpId }` or `crypto.hmac` / a domain-scoped helper).

### RE-3 [blocker | builder] Uncaught `fetch` transport failures poison `CallRecord` as HTTP 400 (72h), and `settle()` ignores disk-save failures at `Run::Await`
- **Where:** `docs/retried-effects.md:11,17-28,83-84`; cross-checked against `crates/tj-cli/src/engine.rs:26,1083`, `crates/tj-core/src/runtime/mod.rs:542-560,650-665,707-718,732-743,771-787`, `crates/tj-core/src/vm/value.rs:131-137`, `crates/tj-core/src/runtime/objects.rs:1006-1041`
- **Case for:** Two real runtime behaviors undermine Option B's core safety claims if left unaddressed:
  1. **Transient `fetch` transport error / 30s `HTTP_TIMEOUT` (`engine.rs:26,1083`) caches a permanent 400 in `CallRecord`:** When Stripe charges a card and the HTTP connection drops or times out (without the tinyjump server crashing), `engine.rs:1083` returns `Input::EffectDone { error: Some("the request failed: ...") }`. `Runtime::resume` (`mod.rs:779`) unwinds with `Exc::with_field` (`vm/value.rs:131-137`), which sets `ExcKind::User` (`is_fault() == false`). An uncaught error in `settle()` (`mod.rs:708-716`) therefore has `effective_status == None`, calls `finish_call` (`calls.rs:331-339`), **permanently caches the error for 72h**, and returns HTTP **400**. The device outbox treats HTTP 400 as final (`docs/host-protocol.md:201`) and stops retrying; retrying with the same `Idempotency-Key` replays the cached 400, while starting a new call generates a new key and **double-charges**. The same permanent-422-caching hazard happens if a post-Step-1 `@invariant` fails (`mod.rs:653,739`) after Step 1's remote charge already succeeded.
  2. **`Run::Await` flush-before-effect claim (`docs/retried-effects.md:11`) fails open on disk error:** `Runtime::fetch` (`mod.rs:558`) pushes `Output::Effect` into `self.outputs` *before* `settle()` runs `flush_from(mark)` (`mod.rs:663`). `settle()` ignores the `bool` returned by `flush_from(mark)`. If `store.save` fails (`objects.rs:1006-1013`), `flush_from` reverts the object in memory and emits `Output::Error`, **but leaves `Output::Effect` in `self.outputs` and the fiber in `self.waiting`** — so Step 2's external effect still fires even though Step 1's checkpoint (`this.chargeId`) failed to reach disk.
- **Case against (cost):** Distinguishing transient `EffectDone` transport failures (or documenting `try/catch` + 503 retry semantics) and aborting/stripping `Output::Effect` when `flush_from(mark)` returns `false` at `Run::Await` are small, surgical fixes (~20–30 lines in `tj-core`), though changing `EffectDone` error status from 400 to 503/500 needs care so intentional `check()`/business errors stay 400 while host transport/timeout errors remain retryable.
- **Proposal:** Add both failure windows explicitly to `docs/retried-effects.md`: (a) specify the `settle()` fix so a failed `flush_from(mark)` at `Run::Await` cancels the fiber and strips uncommitted `Output::Effect`s (never emitting an effect whose preceding checkpoint failed to save); (b) decide and document how `call_once` handles transient `fetch` transport errors (e.g. mark `Effect::Http` transport errors retryable via `refuse_start` / 503 rather than caching a 400 `CallRecord`, or document explicitly why apps must catch and handle them) and note the `@invariant`-at-`await` interaction.

### RE-4 [blocker | builder] Canonical `Order.pay` example has two bugs (`res.body` does not exist; early return drops Step 2 after crash)
- **Where:** `docs/retried-effects.md:59-77`; cross-checked against `crates/tj-core/src/vm/prelude.tj:88-97`, `docs/language.md:346-352`
- **Case for:** Agents copy patterns verbatim from design notes and docs:
  1. Line 68 writes `JSON.parse(res.body).id`, but `fetch` in `vm/prelude.tj:88-97` returns `{ status, ok, headers, text(), json() }` — `res.body` is `null`! It also skips checking `res.ok` before parsing and persisting `this.chargeId`.
  2. Line 60 writes `if (this.chargeId !== "") return this.chargeId`. If the server crashes during Step 2 (`api.mail.example/send`, lines 71–75), `this.chargeId` was already flushed at line 71's `Run::Await`. On retry, line 60 returns immediately and **Step 2 (the receipt) is silently skipped forever**, contradicting the multi-step claim on line 84.
- **Case against (cost):** Zero runtime cost; pure doc fix.
- **Proposal:** Fix the example to check `res.ok`, use `(await res.json()).id` (or `res.json().id`), and guard each step independently (`if (this.chargeId === "") { ... }` then `if (!this.receiptSent) { ... this.receiptSent = true }`), or explicitly note that best-effort notifications belong in outgoing webhooks rather than inline Step 2.

### RE-5 [gap | builder] Step-label collisions in loops, repeated helper calls, and `tj:agent` multi-step `invoke()` turns
- **Where:** `docs/retried-effects.md:106,109,134-135`; cross-checked against `plugins/agent/plugin.tj:17-46`, `crates/tj-core/src/runtime/calls.rs:235-278`
- **Case for:**
  1. Static labels inside loops (`for (const item of items) { await fetch(..., { idempotency: "ship" }) }`) or helper methods called twice in one turn (`this.notify(customer); this.notify(staff)`) produce identical `(object_key, method, caller_tag, root_id, step)` keys. Downstream APIs will silently return item 1's result for items 2..N (or fail with 422), causing silent data loss.
  2. In `tj:agent` (`plugins/agent/plugin.tj:22-44`), `act()` runs `while (steps < maxSteps)` and `for (const call of reply.calls) await invoke(skill.object, skill.method, ...)`. Propagating `parent_call_id` into `invoke()` causes **collisions** whenever the model calls the same `(object, method)` twice in one turn (e.g. booking two slots or sending two messages). Worse, `complete()` is non-deterministic across a crash + retry, so `parent_call_id` propagation cannot make an LLM agent loop crash-idempotent anyway.
- **Case against (cost):** Documenting unique-per-effect step labels (e.g. `` `ship:${item.id}` ``) is free; runtime duplicate-key detection within one call chain (a small `HashSet` or `Vec` of emitted keys on `Fiber` / active call, behind `#[cfg(feature = "server")]`, throwing a clear fix-hint error on reuse) costs ~15 lines and catches loop/helper bugs immediately instead of failing silently.
- **Proposal:**
  1. Document the loop/helper rule (include the item/entity id in `step`, e.g. `` `ship:${item.id}` ``) and specify whether the runtime detects and rejects duplicate derived keys within a single live call (recommended: fail fast with a fix hint).
  2. Revisit `invoke()` propagation: either include a deterministic discriminator or drop the claim that `parent_call_id` makes `tj:agent` loops crash-idempotent, explaining that agent-invoked mutating tools should key on domain entity ids (e.g. slot/order id) rather than LLM turn order.

### RE-6 [gap | builder] Device-build behavior & "0 bytes" claim, `Runtime::secret` for `Who::System`, and case-insensitive `Idempotency-Key` header handling
- **Where:** `docs/retried-effects.md:87,104,108,115,133,137`; cross-checked against `crates/tj-core/src/runtime/privacy.rs:84-105`, `crates/tj-core/src/vm/builtins.rs:25,241-255`, `crates/tj-core/src/typeck.rs:142-155`, `crates/tj-core/src/flow.rs:952-959,1034-1037`, `crates/tj-cli/src/engine.rs:1068-1074`
- **Case for:** Four implementation-facing details are inaccurate or left open:
  1. **Device builds are not literally 0 bytes, and behavior is undecided:** `typeck.rs:142`, `vm/builtins.rs:25`, and `builtins::fetch` compile on WASM/Android/iOS (devices compile `.tj` source at startup, `docs/vision.md:208`). Even a stub + type signature costs ~0.3–0.8 KB (tiny, just don't promise "0 bytes"). Line 137 leaves device behavior ambiguous ("deterministic/random fallback or compile-time server-only hint") — pick one clear rule before coding (failing with a clear fix hint when used in non-`@server` code aligns best with `docs/vision.md` Goal 1 and avoids false crash-safety promises on devices).
  2. **`Runtime::secret` under `Who::System` and store errors:** `caller_tag` (`privacy.rs:85`) returns `"system"` *before* loading/creating `tj:secret`. Implementation needs a shared `store_secret()` helper, and if `store.load`/`store.save` of `tj:secret` fails, `crypto.idempotencyKey` / `fetch({ idempotency })` must fail closed with 503 (never fall back to a random key, which would double-charge on retry). Also check `self.strong` before generating `tj:secret` on first use (matching `secure_bytes`, `mod.rs:514`).
  3. **Case-insensitive header check and `headers: null`:** `docs/language.md:346` uses lowercase headers (`accept`). `docs/retried-effects.md:115` must check `Idempotency-Key` ASCII case-insensitively (`k.eq_ignore_ascii_case("idempotency-key")`) and handle `headers: null`/omitted; consider throwing an error if *both* `idempotency` and an explicit `Idempotency-Key` header are passed rather than silently ignoring `idempotency`.
  4. **PII flow-check interaction (`flow.rs`):** Note explicitly that `flow.rs:1034` treats `crypto.*` as a clean sanitizer (safe here because output is keyed HMAC), while `flow.rs:957` treats all `fetch` option fields as sinks (so `fetch(url, { idempotency: this.email })` will fail closed as an unrevealed PII sink unless `crypto.idempotencyKey(...)` is used).
- **Case against (cost):** Specifying these four details adds ~10 lines to the design note and prevents subtle implementation bugs and review churn in the code PR.
- **Proposal:** Pin down all four points in `docs/retried-effects.md` before starting the implementation PR.

### RE-7 [watch | visionary, builder] Surface area ("one way to do each thing"), optional `tj check` warning noise, and Option A steel-man
- **Where:** `docs/retried-effects.md:44,110,123,136`
- **Case for:**
  1. **One way vs two ways (`AGENTS.md` / `docs/vision.md` Goal 1):** Adding both `crypto.idempotencyKey(step)` AND `fetch(url, { idempotency: "step" })` creates two ways to set `Idempotency-Key` on `fetch`. Keeping only `crypto.idempotencyKey(step)` (`headers: { "Idempotency-Key": crypto.idempotencyKey("charge") }`) gives strictly one surface across `fetch`, custom headers, bodies, and plugins, with zero new `fetch` option parsing or header-precedence edge cases. Conversely, `{ idempotency: "charge" }` is more concise for standard IETF `Idempotency-Key` APIs and harder for agents to mistype the header name. Both sides are valid — worth a quick owner call.
  2. **Advisory `tj check` warning (line 123):** Warning on every non-GET `fetch` without `idempotency` will emit noisy false positives on legitimate non-idempotent/read-like POSTs (OAuth token refresh, search/GraphQL POSTs, LLM APIs) and existing examples. Keep it out of the initial PR or restrict/document carefully.
  3. **Option A comparison fairness (line 44):** Production replay engines (Temporal/Restate) pair journals with deterministic external idempotency keys (`workflow_id + activity_seq`), so claiming Option A "No — still double-charges" slightly straw-mans it. The decisive reasons to reject Option A in tinyjump are already strong on their own: live-reload non-determinism (`tj reload`), `@pii` retention/erasure hazards in cached third-party responses, `TJ_MAX_OBJECT_BYTES` (256 KB), and core size/complexity.
- **Case against (cost):** Small doc tightening (~5 lines) and one quick scope confirmation on whether `fetch({ idempotency })` sugar is worth the second surface.
- **Proposal:** Tighten the Option A row to credit external keys while keeping the rejection firmly grounded in live reload, `@pii`, object byte caps, and core size; confirm with the owner whether to ship both `crypto.idempotencyKey(step)` and `fetch({ idempotency })` or just `crypto.idempotencyKey(step)`; defer the `tj check` warning until real-world usage shows whether it helps or creates noise.
