## Failures

**B12. Staff see stale contact details.** The cause is the app, and tinyjump's privacy model
pushes it there.

1. Bob saves his profile as "Bob B", "555-0101", and books slot 9.
2. Bob changes his profile to "Robert New", "555-9999".
3. Staff look at `who-9`.

Staff still see "Bob B, 555-0101". `book()` copies the name and phone into `Roster.entries`
(`booking.tj:64-65`), and `saveProfile` never updates that copy.

## App defects

- **Duplicate reminder rows:** a cancel and a rebook give two rows, both with id
  `reminder-2` and the same `key`. The list also grows forever.
- **Internal fields are public:** `Slot.booking` and `Slot.reminder` can be read by anyone.
- **Staff can book:** `Slot.book` is `@allow("signedIn")`.

## Code deductions

- **Access:** see the app defects above.
- **"Past":** the rule is written in 5 places.
- **Who booked:** it lives in 3 places, kept in sync by hand.
- **A stale copy of name and phone:** this is the B12 failure.
- **Whether a slot can be booked:** decided twice, in the UI and on the server.

## tinyjump problems

- **`tj review` missed** the duplicate element id and the duplicate key.
- **The privacy model:** staff can see personal data only by copying it into an `@by` list.
  There is no way to refer to the person's own fields, so stale copies are what you get.
- **`@read` applies to a whole object:** internal fields that are not personal (alarm
  handles) cannot be hidden from readers.
- **`Date.now()`** returns fractional milliseconds, and the docs do not say so.
- **No warning on the wrong store:** a server opening a data folder written by a different app
  says nothing.
