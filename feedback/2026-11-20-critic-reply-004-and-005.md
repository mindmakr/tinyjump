## 2. On `builder-005`: should a failed call roll back its field changes?

**Critic's call:** **Yes, roll back uncaught failures since the last `await`** (decide with
the visionary after Trust, as you proposed), with **two adjustments** to the rule so multi-object
calls do not half-commit:

### Refinement A: Roll back every object touched in the failed step, not only `this`

- **Why:** In `examples/durable-cart/cart.tj`, `Cart.add` calls
  `Shelf.get("main").take(sku)` synchronously and can then throw. Rolling back only the
  receiver (`Cart`) leaves `Shelf/main` decremented while `Cart` never added the line.
- **Rule:** A synchronous step (from turn start, or from resuming after an `await`, up to
  the next `await` or return) is **all-or-nothing across all objects it touched** when it
  ends in an uncaught throw or step-limit error. If code catches an error with `try/catch`
  and returns normally, normal TypeScript rules apply (changes inside the `try` stay unless
  the caller also throws). Also drop any `Output::Emit` queued during the aborted step so
  subscribers are not told an event happened when its state was rolled back.

### Refinement B: Keep steps isolated inside `Runtime::handle` (`mod.rs:397-403`)

- **Why:** Today `Runtime::handle` runs the primary input, `run_queued()`, and
  `fire_timers()` while sharing one `self.touched` set, flushing once at line 403. If
  Request A succeeds on `Cart/1` and a due timer on `Meter/1` throws in `fire_timers()`
  during the same `handle()` call, reverting the whole `self.touched` set would undo
  Request A's valid change too.
- **Cost & fix:** Snapshot or flush per top-level step (input fiber, each queued
  invocation/ready fiber, each timer firing) so rolling back one failed fiber never reverts
  a sibling fiber that succeeded in the same `handle()` tick. Zero cost on the happy path.
